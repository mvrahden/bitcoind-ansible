# Changelog

## 2.0.0 — 2026-08-01

### Breaking

- `bitcoind_pgp_builders_pub_key_core` and `bitcoind_pgp_builders_pub_key_knots`
  are removed. Playbooks that set them still run and emit a warning. Use
  `bitcoind_gpg_trusted_fingerprints` to narrow trust instead.
- The systemd unit moves from `/lib/systemd/system/` to `/etc/systemd/system/`.
  The role removes the old copy, so no manual cleanup is needed.
- Ubuntu 20.04 is no longer tested. Its standard support ended in April 2025.
- The generated `bitcoin.conf` no longer carries the copied upstream commentary.
  Option documentation lives in the README.

### Fixed

- **`bitcoind_server: false` silently did nothing.** The line was omitted rather
  than set to `0`, and `bitcoind` defaults `-server` to `1`, so the RPC server
  stayed enabled. This is the only case where 2.0 renders a different effective
  configuration than 1.x.
- The health check ran before the restart handler, so on a configuration change
  it validated the daemon's previous configuration and the version cookie
  recorded success before the restart had happened. Handlers are now flushed
  first.
- **The role could not install any Bitcoin release newer than the pinned
  default.** Verification required attestations from two named builders per
  implementation, but Guix attestation is voluntary and the signer set changes
  every release. `laanwj` stopped attesting after Core 30.2 and `shiny` is absent
  from the current Knots release, so both produced a bare HTTP 404 partway
  through installation.
- **Expired signing keys passed verification.** `gpg --verify` exits 0 for
  `EXPKEYSIG`, and only the exit code was checked. Knots 29.3.knots20260508
  ships such a signature today, from `luke-jr` — one of the two keys the role
  required.
- A per-signer attestation was never bound to that signer's identity:
  `gpg --verify` succeeds if any key in the keyring made the signature.
- Architecture detection mapped anything that was not `aarch64` to `x86_64`,
  silently installing wrong-architecture binaries on 32-bit ARM and riscv64.
- Tor-only mode never published an onion address. `listenonion` needs access to
  Tor's control port and the service account was never granted it, so the daemon
  started normally and stayed inbound-invisible.
- `ansible.posix` was used but declared nowhere outside the test image, so a
  Galaxy install failed as soon as the mount feature was used.
- Two Galaxy tags were invalid: tags may not contain hyphens.

### Added

- `bitcoind_config`, an arbitrary `bitcoin.conf` passthrough applied last, so it
  overrides anything derived from the named variables. This reaches every option
  the role does not name explicitly, including `prune`, `dbcache`,
  `maxconnections`, `blockfilterindex`, `maxuploadtarget` and `datacarriersize`.
- `bitcoind_network_config` for options scoped to the active network.
- `bitcoind_tor_enabled`, which wires up `proxy`, `listenonion` and `torcontrol`
  together and grants control-cookie access through `SupplementaryGroups`.
- A threshold verification model: `bitcoind_gpg_min_valid_signatures` (default 3,
  matching Bitcoin Core's own tooling), `bitcoind_gpg_trusted_fingerprints` and
  `bitcoind_gpg_allow_expired_keys`.
- Builder public keys bundled in `files/builder-keys/`, regenerated by
  `scripts/update-builder-keys.sh`. Installs no longer depend on a keyserver.
- A post-start RPC health check, `bitcoind_health_check`, skipped automatically
  when the RPC server is disabled.
- `bitcoind_no_log`, so a configuration change can be previewed with
  `--check --diff` at the cost of showing the `rpcauth` hash.
- `files/builder-keys/<implementation>/MANIFEST`, mapping each builder to the
  primary key fingerprint verification matches on. An armored key block is not
  human-reviewable in a diff; a fingerprint list is.
- [docs/MIGRATION-2.0.md](docs/MIGRATION-2.0.md).
- Preflight validation for the `prune` × `txindex`/`coinstatsindex` conflict,
  unsupported architectures, non-Debian systems, and a missing Tor group.
- Debian 12 and 13 and Ubuntu 24.04 in the test matrix, alongside Ubuntu 22.04.
- A molecule scenario covering the upgrade path, which exercises the version
  cookie logic that a fresh-install test never reaches, and a side effect stage
  in the default scenario covering a configuration-only change, asserting the
  new setting reaches the running daemon rather than only the file.
- `yamllint` and `ansible-lint` in CI, passing at ansible-lint's production
  profile.
- A weekly workflow that opens an issue when the pinned defaults fall behind
  upstream.
- A `LICENSE` file. MIT has been declared in `meta/main.yml` since the project
  began, but the licence text was never committed.

### Changed

- Defaults move to Bitcoin Core 31.1 and Bitcoin Knots 29.3.knots20260508.
- `bitcoin.conf` is assembled as a single merged dictionary and rendered once,
  so every key is emitted exactly once. Duplicate keys previously could not be
  ruled out, and Bitcoin Core's precedence for them is easy to get wrong.
- Tightened permissions on the data directory, the downloaded release tarball
  and the extraction directory.
- Removed `setup.sh` and `docs/bitnodes-setup.sh`, neither of which had anything
  to do with this role.
